# 插件分发与开发体验（设计草案）

> **状态：草案 v1 —— 最小闭环已落地，后续阶段未实现。**
> 本文记录「为什么这样切」以及「哪些还没做」；**当前行为以《插件开发.md》为准**，
> 两者冲突时以插件开发文档 + 代码为准。真源仍是代码。

## 1. 问题

插件能力面（权限、描述式 UI、沙箱）本身够用，真正拖住作者的是**开发与分发两端的摩擦**：

| 环节 | 落笔前的状态 | 证据 |
|---|---|---|
| 改一行代码 | 网页里「复制 → 粘贴 → 安装 → 启用」四步，无文件监听、无自动启用 | 插件面板只能上传文件 / 粘贴 URL |
| 清单写错 | 必须安装后才知道；TS 转译错误也要等上传 | 校验只在 `createFromCode` 里 |
| 兼容性 | 插件没有任何「我需要哪个 SDK」的表达；旧宿主装上依赖新 API 的插件只会在运行时抛 `undefined` | manifest 只有 5 个字段 |
| 组合 | 插件不能声明依赖另一个插件，也没法在安装/启用时判断「缺了什么」 | 无 `dependencies` |
| 市场信息 | `index.json` 只有 name/version/perms/hosts；版本要求只能手写进官网文案 | `sync-plugins.mjs` |

## 2. 目标与非目标

**本期目标（已落地）**

1. 终端里完成「校验 → 安装 → 启用 → 保存即重推」的开发循环。
2. 清单能表达两种约束：宿主 SDK 要求（`engines`）与插件间依赖（`dependencies`）。
3. 约束的判定只有一处实现：服务端 Go 规则；开发工具与安装路径共用（`POST /api/plugins/validate`）。
4. 分发数据随 manifest 走：`index.json` 透出 `engines` / `dependencies`，市场卡片可见。

**本期不做（明确留在后续）**

- 插件间通信总线（`api.bus`）、跨插件数据共享——这会引入「插件 A 能否信任插件 B」的新信任边界，需要单独设计。
- 更丰富的 UI 表达（自定义 CSS / 栅格 / 图表组件）、沙箱能力放宽（Worker / IndexedDB / 流式 AI）。
- 浏览器侧热重载（推送到启用后仍需刷新页面；没有做 WS 通知前端重挂载）。
- 市场评分 / 审核 / 安装量——属于运营体系，不是开发者体验。

理由：前两项动的是安全模型，应该单独评审；最后一项依赖服务端新表与运营流程，和本期的「约束契约」不是同一层。

## 3. 方案

### 3.1 清单字段

```json
{
  "engines": { "sdk": ">=5" },
  "dependencies": ["word-count@^1.0.0"]
}
```

- `engines` 只有 `sdk` 一个键：**未知键直接报错**。engines 是新字段，静默忽略拼错的键（`sdks`）会让作者以为兼容性检查生效了，宁可装不上。
- `dependencies` 最多 10 项，名字字符集 `[A-Za-z0-9_.-]`（`@` 是分隔符，名字里出现会让 `name@range` 有歧义），禁自依赖与重复。
- 版本约束共七种：`*` `=` `>` `>=` `<` `<=` `~` `^`，npm 语义。不支持预发布与 `||`——声明越简单，宿主与开发工具越不会各解释各的。

### 3.2 判定时机（关键决策）

| 约束 | 安装时 | 启用时 |
|---|---|---|
| `engines.sdk` | **拒绝**（400） | 不重复检查 |
| `dependencies` | 只校验语法 | **拒绝**（403，带未满足列表） |

理由：

- **SDK 不满足 = 代码跑不起来**，装上也只会在运行时抛 `undefined`，那是比安装报错更难查的故障。
- **依赖未就绪 = 现在还跑不起来**，但「先装使用者、后装被依赖者」是一次导入多个插件的常态；安装阶段拦截会让批量导入做不了。
- 启用时要求依赖**已安装 + 版本符合 + 已启用**。装了但停用的依赖同样提供不了能力，放行只会在运行时炸。三种原因分开报（未安装 / 版本不符 / 未启用），因为处理动作完全不同。

### 3.3 开发循环

```
编辑文件 → dev-plugin check（离线/在线同一套规则）→ push（上传 + 启用）→ 刷新页面
```

- 离线校验是 Go 规则的**镜像**，用于 CI 和没有服务端的场合；在线校验走 `POST /api/plugins/validate`，与安装共用实现。脚本明确以在线结果为准。
- 干跑接口返回 200 + `{ok, manifest, errors, notes}` 而不是 400：CLI 要一次列清全部问题，而不是修一条报一条。
- 认证：`--token` / `MC_TOKEN` / `--user --pass`。启用了两步验证的账号无法走密码登录，脚本直接报错而不是假成功。

### 3.4 存储

`plugins` 表新增 `engines` / `dependencies` 两列（迁移 `0037_plugin_distribution`），以 JSON 串存储，安装/升级时整体覆盖。不拆关系表：这些字段只在安装时写一次，读取走响应体，拆表只会多一次 join。

## 4. 兼容

- 旧插件（无 `engines` / `dependencies`）行为不变，两列留空即「无约束」。
- 旧客户端（不认识新字段）不受影响：字段只增不改，服务端仍是校验方。
- `index.json` 新增两个键；官网对缺失字段做了兜底（`engines ?? {}`、`dependencies ?? []`），旧索引不会崩。
- 升级路径：`engines` 误判的机会成本最高，因此它只在**安装/升级**时判一次，已在库的旧版本不受追溯影响。

## 6. 后续路线（未实现）

按建议顺序，每一步都应先补设计再动代码：

1. **插件设置页标准化**：`api.settings.render(desc)` + 插件在自己的命名空间持久化，抽屉里直接进设置；现在只能借 `addPage` 做一个全站页面。
2. **插件间通信**：最小可行形态是「提供方声明 `provides`、使用方声明 `consumes` + 依赖」，宿主只在这些成对的插件之间路由消息；不做全局广播。
3. **浏览器侧热重载**：`watch` 推送成功后由服务端经 WS 下发 `plugin:updated`，前端宿主自动重挂载，省掉刷新。
4. **调试面板**：把沙箱 `console.*` 带插件名前缀桥接到宿主，并在抽屉里开一个「调试」页；当前只能翻 DevTools 的 frame 列表。
5. **市场运营层**：安装量 / 评分 / 审核队列。需要新表与后台，属于独立项目。

## 7. 风险与回滚

- 改造点集中在清单解析与启停路径，回滚只需回退提交 + `0037` 的 down 迁移（`DROP COLUMN` 两条）。
- 依赖检查只作用于「启用」这一个动作，失败时插件保持停用，不会出现半启用状态。
- 干跑接口与上传共用限流桶（`pluginLimit`）与请求体上限，避免成为免登录的 CPU 消耗点（接口本身需登录）。
